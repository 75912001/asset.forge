# 宝箱类型、掉落包与开启约定

## 配置身份

- 宝箱类型统一维护于 chest_type 枚举, 项目包含 key、label、value 和 icon, 可选 max 表示闭区间终值, 不属于资产分类, 不参与奖励发放.
- 所有枚举项支持可选 PNG; 宝箱类型非零项必须有 PNG, undefined=0 无图标且不能作为包类型. 多个掉落包可以共用同一类型.
- 玩家持有的是掉落包 ID 和数量. 相同图片不会让不同掉落包合并堆叠.
- 普通资产 ID 和掉落包 ID 使用现有的不重叠分类范围. 宝箱枚举值可以与资产 ID 相同, 不能拿它代替奖励目标 ID.

## 编辑流程

1. 在当前项目 assets/ 中放入 PNG, 进入"枚举管理"编辑"宝箱类型", 选择图标后保存. 新项目启用掉落包时只创建含零项的枚举, 不复制图片.
2. 进入"掉落包", 创建或选择包, 明确指定非零"宝箱类型". 类型预览和列表缩略图来自同一枚举项. 范围内的数值匹配所属类型, 已保存的内部值回显并原样保留, 不改成范围起值.
3. 添加奖励组合, 在奖励选择器中选择普通资产或掉落包, 设置数量和万分率概率.
4. 保存整个包及条目. 页面与服务端使用相同校验, 无效配置不提交, 失败保留草稿.
5. 资产表、枚举和掉落包的未保存草稿互相隔离, 保存或放弃后才允许编辑其他配置; 跨项目切换和导出也会阻止未保存草稿. PNG 选择期间也阻止切换.

## 非空保障

所有掉落包至少有一个有效组合; 所有组合至少有一个概率为 10000 的奖励项. 数量必须大于 0, 奖励目标必须存在.

- 权重模式: 权重为正, 每次选中一个组合; 该组合内的必得奖励保证结果非空.
- 概率模式: 在上述条件之外, 至少一个组合的命中概率必须为 10000. 即使命中概率为 0 的其他组合, 内部仍必须有一项必得奖励.
- 组合与奖励项分别独立判定. 10000 表示 100%, 5000 表示 50%.
- 失败提示包含掉落包 ID 和相关组合 ID. 不会自动把概率补成 100% 或创建虚构奖励.

## 引用完整性

保存、导出以及服务端接收配置时都验证宝箱类型和奖励目标. 修改枚举时不能使已使用的数值失去原类型归属, 名称和图标可以更新. 删除仍被其他奖励列表引用的资产/掉落包会失败. 启用掉落包后 chest_type 标识及核心字段的枚举引用不可修改.

掉落条目和宝箱类型不能被当成奖励. 掉落包可以引用自己或其他掉落包作为待开启物品, 这不是递归发奖; 设计者仍需自行评估循环奖励的经济风险.

## YAML

工作区使用 enums[].items[].icon, 未填图标时省略该字段. asset-enums.yaml 示例:

```yaml
version: 1
enums:
  - key: "chest_type"
    label: "宝箱类型"
    items:
      - key: "undefined"
        label: "未定义"
        value: 0
      - key: "wood"
        label: "木箱"
        value: 1
        icon: "icons/chests/wood.png"
```

掉落包表使用必填字段 chest_type, 类型为 enum, enum 引用固定为 chest_type, 行数据仍保存数字. 奖励数组沿用 asset_id、count、probability. 不再导出 chest-appearances.yaml 或 chest_appearance_id. 游戏端加载包时需加载 asset-enums.yaml, 通过 value 到 max 的闭区间查找类型及图片; 没有 max 时按单值匹配. 单表导出仍只导出该表.

## 旧项目升级与恢复

1. 先保存浏览器修改并备份草稿, 停止旧服务, 避免旧版本程序继续写入旧结构.
2. 确认独立外观 ID 与已有 chest_type 枚举值、名称对应, 原图片存在. 同值名称或图标冲突、缺少对应项、无效包引用均明确报错. 更早且没有外观引用的数据需先用兼容旧版本完成前置升级.
3. 在仓库根目录执行 `node scripts/migrate-chest-types.mjs <项目标识>`.
4. 脚本检查数据库、全部 PNG、引用和非空条件后, 将包含已提交 WAL 的完整数据库及相关已有 YAML 备份到 projects/<项目标识>/backups/before-chest-types-r<版本>-<唯一标识>/. 单事务合并图标、替换包字段并移除独立外观记录, revision 增加一次, 奖励原始记录不重写.
5. 脚本重新导出 YAML, 最后移除已备份的旧外观 YAML. 数据库及导出已一致时重复执行不写入; 数据库已迁移但导出未完成时, 可保持停服并重跑命令完成导出.
6. 启动服务并刷新页面, 核对图标、奖励内容与导出. 旧外观草稿无法直接恢复, 请先下载完整备份, 再在枚举中重做修改.

若迁移前的奖励不满足非空条件, 脚本报错并保持数据库不变, 不擅自修补概率. 事务失败回滚并报告备份; 导出失败明确提示数据库已迁移及恢复方法. 如需恢复, 先停止所有使用该项目的进程, 另行备份整个当前项目; 从打印的备份目录恢复 workspace.sqlite 与 cfg 中原有 YAML, 并移除本轮新增且备份中不存在的 YAML, 使用兼容旧程序启动. 不要覆盖仍在使用的数据库或混用旧 WAL 文件. 恢复是显式运维操作, 脚本不会自动回退后续编辑.

## 游戏端执行约定

本次不实现玩家背包和开箱执行. 游戏端应遵守:

- 背包记录掉落包 ID 与数量; 名称、外观、奖励规则读取最新配置. 若要保留旧规则, 发布新的包 ID.
- 成功开启一次, 消耗一个包并发放本次命中的奖励. 两项操作必须处于同一原子事务或等效的一致性流程.
- 同一开启请求必须具备幂等标识, 重试不能重复消耗或发奖.
- 获得的掉落包只写入背包, 不自动展开. 因而引用环不会在当前抽取过程中递归执行.
- 不能把数据库或网络失败当成正常空奖励结果, 也不能通过无限重抽掩盖无效配置.
