# 推送git

将当前 Asset Forge 的代码, 图片, 共享技能和已保存项目数据一起交付, 以独立副本实际运行作为验收. 使用当前会话已授权的提交和推送范围, 不因技能被自动选中而扩大外部写入授权.

## 准备数据与资源

- 从仓库根目录读取 AGENTS.md, README.md, .gitignore, 当前分支, 远端, 暂存及未暂存差异. 使用已有分支和远端约定, 不另建仓库或改写历史.
- 按正常编辑器流程保存本次需要交付的页面修改. 浏览器未保存草稿不属于 SQLite 数据, 不能声称已随 Git 提交; 不把草稿内容猜填到数据库.
- 记录本地服务是否运行, 数据保存后按 README 停止本仓库服务. 对每个项目的 SQLite 执行完整性检查并完成 WAL checkpoint; 未成功合并时停止提交, 不能只提交旧主库或删除 WAL 掩盖失败. 结束后按原运行状态恢复服务.
- 对照数据库检查并使用现有导出流程同步各项目 cfg/ 的分类, 枚举及资产 YAML. 已保存 SQLite 是数据来源, 不用旧 YAML 或 seed 覆盖当前数据库.
- 纳入每个 projects/<项目标识>/ 的 project.json, workspace.sqlite, assets/ 和 cfg/, 以及代码, 启动文件, package.json, 锁文件, 共享技能和参考图. 检查新增资源是否被忽略; 新技能同时更新 AGENTS.md, README.md 和 .gitignore 的技能白名单.
- 保留已有原始资源, 提示词和迁移用的旧数据文件. 运行日志, server.pid, SQLite 临时文件, node_modules, 构建缓存, 本机验证截图, 已忽略的迁移前备份与密钥不因"全部提交"而强制加入. 意外发现缺失资源, 损坏数据库或敏感文件时明确报告, 不初始化空库或生成占位图绕过.

## 更新到最新并解决冲突

1. 提交前先确认已有目标远端和分支, 执行 `git fetch <远端>` 获取最新状态. 获取失败时停止, 不基于过期的远端跟踪分支继续提交.
2. 本地修改妨碍分支更新时, 在保存页面, 停止服务并完成 WAL checkpoint 后, 使用可恢复的备份或 `git stash push -u` 保护已暂存, 未暂存及未跟踪文件, 记录备份位置或 stash 标识和原暂存范围. `-u` 不包含被忽略文件, 受更新影响的此类文件需单独保护. 不先做临时提交绕过更新顺序, 不丢弃本地修改.
3. 可快进时执行 `git merge --ff-only <远端>/<分支>`; 分支分歧时使用 `git merge --no-commit <远端>/<分支>`, 保留双方历史. 按下述规则处理冲突并通过"提交前验证"后, 才能完成合并提交. 不自动 rebase 或改写已有提交.
4. 文本冲突结合共同祖先, 本地和远端的修改意图逐项解决, 不盲目整文件选择 ours/theirs. SQLite, PNG 等二进制冲突保留双方版本, 不用旧 YAML 重建数据库或直接覆盖一方. 无法根据现有需求确定取舍时, 展示具体冲突并询问用户, 未解决前不提交.
5. 分支更新及合并提交完成后, 恢复此前保存的本地修改, 保留无关修改及其暂存范围, 按同一规则解决恢复时的冲突. 使用 stash 时先 apply, 核对恢复完整后再删除对应 stash, 不直接 pop. 合并或恢复后重新检查 SQLite 完整性, 根据最终数据库重新导出 YAML, 再进入本次改动的验证和提交.

## 提交前验证

1. 确认 `git ls-files -u` 无输出, 核对暂存文件清单及 `git diff --cached --check`, 不带未解决冲突或冲突标记提交. 只暂存本次授权范围, 不清除或覆盖其他已有修改.
2. 将暂存区导出到新的临时目录, 例如 `git checkout-index --all --prefix=<独立目录>/`, 不复制工作区的 node_modules, 未跟踪资源或本机配置.
3. 在仓库根目录运行 `node .agents/skills/push-git/scripts/verify-clone.mjs <独立目录>`. 脚本启动独立目录的本地服务, 检查全部已登记项目的 SQLite, 页面与静态文件, YAML 导出内容和 PNG 引用. 它会写入副本的运行文件, 因此不能对正在编辑的工作区执行. 验证失败则停止提交推送并报告具体失败项.
4. 按实际改动运行必要测试. 仅本地编辑器运行不需要 npm install, 构建, Cloudflare 或 ChatGPT 登录. 不为通过验证擅自安装依赖或更改本机环境.

## 提交与推送

- 使用概括实际变更的提交说明创建普通提交, 普通推送到已有目标分支. 用户已明确要求本次推送时直接完成, 不重复确认; 缺少推送授权时先准备并验证可审阅的提交内容, 再请求该项授权.
- 推送因远端新增提交而被拒绝时, 按上述流程重新获取并合并最新内容, 解决冲突, 重新验证后完成所需提交, 再普通推送重试一次. 再次被拒绝或出现其他拒绝原因时停止并报告具体原因, 不强推或覆盖他人提交. 网络或认证失败明确报告, 不无限重试或改动凭据.
- 推送后核对远端分支 SHA 与本次提交一致, 从该远端分支重新 clone 到另一独立目录并再次运行验证脚本. 推送后的验证失败应明确说明提交已在远端, 不自动回滚远端历史.
- 汇报提交 SHA, 目标分支, 实际纳入的资源与数据, 独立 clone 的验证结果和限制. 仅本地提交不称为已推送, 仅 HTTP 健康检查通过不称为数据与资源完整.
